Everything a person does in a [workspace](/devic/workspaces/index) can also be
done from code, under `/v1/workspaces` of the public API or with
`devic workspaces` (alias `devic ws`) in the [CLI](/devic/cli/index). The same
permissions apply. Membership and roles are checked exactly as in the app.

---

## Who a request acts as

Workspaces belong to people, so the first thing each request settles is who it
acts as.

| Credential | `X-Devic-User` header | Acts as |
|---|---|---|
| A person's token (CLI login, OAuth app) | — | That person |
| API key | userUID or email of a person of the key's account | That person, with **their own** permissions |
| API key | not sent | The **account integration**, shown as "API" |

- **Acting for a person never adds permissions.** An admin key acting for a
  consumer user can only do what that consumer can do in the app.
- **The account integration has no person behind it.**
  - It sees the account's **shared** workspaces only, never personal workspaces
    or private conversations.
  - It acts as a workspace manager, never as an owner.
  - Its messages are signed **API**.
- **Tenant-session tokens are rejected.** They identify your customers, not
  members of your account.

```bash
devic ws me                                   # person or integration, and the origin its messages carry
devic ws --as ana@acme.com me                 # act for a person (or: export DEVIC_USER=ana@acme.com)
```

```http
GET https://api.devic.ai/v1/workspaces/me
Authorization: Bearer YOUR_API_KEY
X-Devic-User: ana@acme.com
```

Every message written this way records where it came from in `origin`:
`channel` (`api`, `cli` or `sdk`) and the credential. The apps show it as a
"via API / CLI / SDK" tag. The server sets it; a request body cannot.

## Find the work

```bash
devic ws list --search ventas --summary          # with thread, unread and document counts
devic ws threads list --unread                   # unread threads across every workspace
devic ws threads list --search renovaciones      # matches the thread title or the workspace name
```

[`GET /v1/workspaces/threads`](/api-reference/endpoint/get-api-v1-workspaces-threads)
covers every workspace you can see, or one with `workspaceId`:

- `search` ignores case and accents, and every word must appear.
- `unread=true` keeps threads with messages from others since your last read,
  or that were marked unread.
- Results come newest activity first, paginated with `offset` and `limit`.
- Each row carries `unreadCount`, `unreadMentionCount`, `waitingForMe` (a
  question or an approval waiting for you) and `activeRunCount`.

## Read a thread

```bash
devic ws threads get <wid> <tid>                    # latest messages and pending questions
devic ws threads messages <wid> <tid> --before 120  # an older page
devic ws threads messages <wid> <tid> --after 164   # only what is new
devic ws threads read <wid> <tid>                   # mark it read
```

- Messages are paged by `seq`, at most 200 per page.
- Each page also returns the runs answering its messages, plus every run still
  in progress.
- Reading never marks a thread read. Use
  [`POST …/read`](/api-reference/endpoint/post-api-v1-workspaces-wid-threads-tid-read)
  for that.

## Write, and wait for the assistant

```bash
devic ws send <wid> <tid> "Resume la semana" --assistant <aid> --wait
```

```http
POST /v1/workspaces/{wid}/threads/{tid}/messages
{ "text": "Resume la semana", "directedAssistantId": "<aid>", "clientMessageId": "weekly-2026-47" }
```

- **Asking an assistant:** set `directedAssistantId`, mention it, or reply to one
  of its messages. The response lists the runs the message started.
- **Retries:** `clientMessageId` makes them safe. The same id and body return the
  same message.
- **`@everybody`:** add `{ "kind": "everyone", "id": "everyone", "label": "everybody" }`
  to `mentions` and `@everybody` to the text (`devic ws send … --everybody`). It
  notifies everyone who can read the thread and never asks an assistant. Not for
  guests from another account; once every 10 minutes per author and thread (`429
  EVERYONE_MENTION_COOLDOWN`, the message is not posted).
- **`--wait`:** the CLI follows the runs until they finish or wait for you.

## Direct messages

```bash
devic ws dm list
devic ws dm send ana@acme.com "¿Revisas la factura?"
```

```http
GET  /v1/workspaces/direct-messages            → { "workspaceId": "<space>", "items": [ … ] }
POST /v1/workspaces/direct-messages  { "email": "ana@acme.com" }   // or "userUID"
```

- Private conversations are account-wide and live in one hidden space of the
  account. Use its `workspaceId` with the usual thread endpoints to read, write,
  mark read or download files. It is `null` until the first conversation.
- Opening a conversation with someone you already talk to returns the same one.
- They need a person: the account integration (an API key without
  `X-Devic-User`) gets `403 DIRECT_MESSAGES_REQUIRE_USER`.
- `GET /v1/workspaces/threads?kind=direct` lists them among the rest.

## When the assistant waits for you

A run in `waiting_input` asked a question. A run in `waiting_approval` wants to
use a tool that needs approval.

```bash
devic ws answer <wid> <tid> <runId> --answers '[{"id":"periodicidad","selected":["anual"]}]'
devic ws approve <wid> <tid> <runId>
```

Through the API, use
[`POST …/invocations/{runId}/{action}`](/api-reference/endpoint/post-api-v1-workspaces-wid-threads-tid-invocations-runid-action):

- **`answer`:** `{ revision, inputId, response: { answers } }`, or `skipped: true`
  to skip the questions.
- **`approve`:** `{ revision, actionId }`, where `actionId` is the run's
  `requestedAction.id`.
- **`cancel` and `retry`** take the same route.

A stale `revision` returns `409`: read the thread again and retry. The CLI fills
in `revision`, `inputId` and `actionId` for you.

## Files and documents

```bash
devic ws files list <wid> <tid>
devic ws files download <wid> <tid> <fileId> --out ./out/   # never overwrites without --force
devic ws documents <wid> --search contrato
```

The download is the original file, with its name in `Content-Disposition`.

## Configure a workspace

Settings, members, assistants, knowledge and skills, rules, core memory and
automations are all available:

```bash
devic ws members set <wid> <userUID> --role member
devic ws skills attach <wid> <skillId>
devic ws rules set <wid> --file rules.md
devic ws memory add <wid> <aid> --section decisions --content "Prices are quoted in EUR" --pinned
devic ws automations list <wid>
```

Each needs the same [role](/devic/workspaces/index#roles) as in the app. Changes
that carry a revision (rules, resources, members, assistants) refuse a stale
one with `409`.

## Build an automation

An automation reacts to an app event, runs on a schedule or runs on demand, and
posts its results in a workspace. In the app, the Automations assistant designs
it with you. Through the API and the CLI you compose it yourself, with the same
information and the same validation:

<Steps>
  <Step title="See what it can use">
    ```bash
    devic ws automations capabilities <wid>    # app events, schedules, included model
    devic ws automations destinations <wid>    # workspaces it may post to
    devic ws automations connections <wid>     # connected accounts it may use
    ```
  </Step>
  <Step title="Connect a missing app">
    ```bash
    devic ws integrations search <wid> "meeting recordings" --semantic
    devic ws connections connect <wid> <app> --scope workspace
    ```
    The response carries the provider's authorization link. The person opens it
    and accepts the consent screen; the account is connected only then. A shared
    workspace needs an account connected for everyone (`--scope workspace`).
  </Step>
  <Step title="Choose the event or the schedule">
    ```bash
    devic ws automations triggers <wid> --integration <app> --query "new recording"
    devic ws automations trigger <wid> <slug>              # configuration and setup instructions
    devic ws automations schedule-preview <wid> --data '{"expression":"0 9 * * 1-5","timezone":"Europe/Madrid"}'
    ```
  </Step>
  <Step title="Grant tools and find the destination threads">
    ```bash
    devic ws automations connection-tools <wid> <connectionId>
    devic ws automations find-threads <wid> <target> --query acme --search-in all
    ```
  </Step>
  <Step title="Save the draft">
    ```bash
    devic ws automations create <wid> --name "Meeting summaries"
    devic ws automations draft <wid> <id> --data plan.json
    ```
    The plan is validated before it is saved: accounts, tools, trigger
    configuration and destination. Saving never activates it.
  </Step>
  <Step title="Activate">
    ```bash
    devic ws automations activate <wid> <id> --included
    ```
    Activation is the approval of that draft version, with the model that runs
    it: the included one, or a provider and model with your own key.
  </Step>
</Steps>

The plan's fields are described in
[Save an automation draft](/api-reference/endpoint/put-api-v1-workspaces-wid-automations-automationid-draft).
These operations need the owner or a manager of the workspace. The same tools
are in the Devic MCP (`https://devic.mcp.devic.ai/mcp`), so an assistant like
Claude can build an automation in a conversation.

## Access

<Note>
  An API key restricted to some endpoints needs the **Workspaces** group
  (`/v1/workspaces/*`) in its [allowed endpoints](/devic/administration/api-keys).
  An OAuth app needs the `workspaces:read` or `workspaces:write` scopes, or a
  `platform:*` scope.
</Note>

The complete list of operations is in the API reference, under
[Workspaces](/api-reference/endpoint/get-api-v1-workspaces).

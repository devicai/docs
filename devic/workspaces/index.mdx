A **workspace** is where a team and its assistants work together. People write in
**threads**, mention an assistant or address one directly, and the assistant
answers in the same thread, with the tools, knowledge and rules the workspace
gives it.

Workspaces live in the web app and the mobile app. Everything they do is also
available [from the API and the CLI](/devic/workspaces/api-and-cli), with the
same permissions.

## Direct messages

Private conversations are account-wide: any two people of the account can write
to each other, whatever workspaces they share. They have their own **Direct
messages** section, next to the workspaces, and only the two participants can
open them and their documents. A document from a private conversation can be
published as a copy in a shared thread.

---

## How an assistant takes part

An assistant answers when someone addresses it, either by mentioning it or by
replying to one of its messages. The workspace can also be set to suggest an
assistant, or to bring one in automatically.

While it works, the run is visible in the thread: thinking, writing, the tools
it calls. Sometimes it waits for a person:

- **A question.** The assistant asks with options or free text, and the run
  continues with the answer.
- **An approval.** Some tools, such as the terminal, need someone to approve
  them before they run.

Through the API these are runs in `waiting_input` and `waiting_approval`, and
you can answer or approve them from there too.

## Roles

| Role | Can |
|---|---|
| Viewer | Read threads, files, rules and memory |
| Member | All of the above, plus write, answer and approve runs, edit memory and thread rules |
| Manager | All of the above, plus manage automations and skills. An account admin who is a manager also edits settings, members, assistants, knowledge and workspace rules |
| Owner | Everything, including ownership |

### Consumer permissions

In a shared workspace, the owner decides what **members whose account role is
Consumer** can do, and the same policy applies to guests from other Devic
accounts. Open **Participants** and find **Role permissions** below the
assistants: a table with what Owner and Manager can do (for reference) and a
switch for each Member permission.

| Permission | Owner | Manager | Member (Consumer) default |
|---|---|---|---|
| Participate in threads and run assistants | ✓ | ✓ | On |
| Create threads | ✓ | ✓ | On |
| Upload, publish and remove thread files | ✓ | ✓ | On |
| Edit the thread canvas | ✓ | ✓ | On |
| Edit thread rules | ✓ | ✓ | Off |
| Edit assistants' shared core memory | ✓ | ✓ | Off |
| Use shared integrations | ✓ | ✓ | On |
| Connect and use personal integrations | ✓ | ✓ | On |
| Edit workspace rules | Account admins | Account admins | Off |
| Create and configure workspace assistants | Account admins | Account admins | Off |
| Manage workspace skills | ✓ | ✓ | Off |
| Manage workspace automations | ✓ | ✓ | Off |
| Manage shared integrations and MCP servers | ✓ | ✓ | Off |
| Invite members and viewers | ✓ | ✓ | Off |
| Change these permissions | ✓ | — | — |

- Every Member permission needs **Participate**: turning it off leaves consumers read-only.
- Workspace management permissions are never given to guests from another account.
- Viewers are always read-only. Members with a User or Admin account role are not limited by this policy, but cannot manage the workspace.
- The policy applies through the API too. To change it there, see [Set consumer permissions](/api-reference/endpoint/patch-api-v1-workspaces-wid-consumer-permissions).

A personal workspace belongs to one person and nobody else can see it.

## Messages written outside the apps

Messages written through the [public API, the CLI or the SDK](/devic/workspaces/api-and-cli)
carry a small **via API**, **via CLI** or **via SDK** tag next to the author. The
tag's tooltip says how the message was sent: by the person through an
authorized app, with an API key on the person's behalf, or by an API key with
no person behind it, shown as **API**.
